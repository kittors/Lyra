# Lyra 中转

一个只做一件事的 WebSocket 中转：让手机和电脑在**谁也听不见谁**的时候还能配上。

## 为什么需要它

局域网配对要求两台设备在同一个网络里。出了门就不成立——手机在流量上，电脑在家里的路由器后面，
双方都没有对方能拨到的地址。公网反代能解决，但前提是你已经有一个域名、一台反代、一条打得进来
的端口转发；大多数人没有。

中转不假设任何一边可达：**两端都主动往外连**它，它把两条连接接在一起。NAT 后面也能用，因为出
站连接从来不需要端口转发。

## 它不知道什么

房间号是配对令牌的 SHA-256，令牌本身不出现在发给中转的消息里。会话帧按字节转发，不解析业务
内容；renderer 资源请求与响应是中转明确处理的例外。

这不是端到端加密：中转仍能读取和注入 WebSocket 帧。房间号本身就是该传输的 bearer capability，
并不需要反推出令牌才能控制房间。WSS 保护两段网络链路，不能隔离中转运营方；必须使用可信的中转。

## 协议

一条连接，第一帧声明身份，之后就是纯转发。

```
客户端 → 中转   {"type":"hello","room":"<sha256>","role":"host"|"guest"}
中转 → 客户端   {"type":"ready"}            对方也在，可以说话了
中转 → 客户端   {"type":"waiting"}          先到的那个，等着
中转 → 客户端   {"type":"peer-left"}        对方断了
```

`ready` 之后的每一帧原样转给房间里的另一个人。中转不缓存、不重排、不落盘。

### 大消息怎么过（version 2）

帧是**边收边转**的：帧头一读到就转出去，载荷来一块转一块，中转手里从不攒整帧。所以一帧多大
不花中转的内存，花的只是一段 socket 缓冲。几件由此而来的事：

- **分片消息保持是一条消息。** FIN 位和 opcode（包括 0x0 延续帧）原样转发。Android 的 WebView
  （Chromium）会把大于约 128 KiB 的消息拆成一串延续帧、在发送繁忙时连 64 KiB 的也拆；version 1
  的中转把每一片都当成一条完整消息重发，桌面端收到一段截断的 JSON 和一串无主的延续帧，按协议
  错误断开——手机经中转连一张照片都发不出去。
- **慢的那一端决定速度。** 某一端待写出的字节超过 1 MiB（`LYRA_RELAY_HIGH_WATER`），就暂停读
  另一端的 socket，等 `drain` 再继续。等待沿 TCP 退回发送方，而不是堆在中转的内存里。一个 60 秒
  （`LYRA_RELAY_STALL_MS`）一个字节都不收的接收方按已断开处理。
- **中转自己的消息只在帧与消息的边界上插入。** `ready`、`peer-left`、`asset_request` 等在对面那
  条分片消息结束后才写；`pong` 可以夹在两片之间，但不能插进某一帧的载荷中间。一端在一帧或一条
  分片消息的中途离开时，另一端的连接会被直接关闭（它已经读了半截，任何新帧都会被当成剩下的载荷），
  由客户端重连并从会话日志补齐。
- **半关闭的连接当作离开。** 手机被杀掉时往往只发 FIN、不发关闭帧；version 1 的中转收不到
  `close`，那个成员一直占着房间的 mobile 位，同一部手机重连被拒为 `role-full`。现在 `end` 即离开，
  另开 TCP keepalive 探测断网后不发任何包的死连接。

上限（都可用环境变量调）：

| 项 | 默认 | 环境变量 | 为什么 |
| --- | --- | --- | --- |
| 单帧长度 | 256 MiB | `LYRA_RELAY_MAX_FRAME` | 不再是内存上限，只是长度字段的合理性检查；新客户端的大数据是 256 KiB 以内的分片，老桌面端会把整份转录放在一帧里 |
| 每条连接累计转发 | 8 GiB | `LYRA_RELAY_MAX_BYTES` | 防失控循环。原来的 1 GiB 在手机能上传最大 2 GiB 的文件（可续传）之后会把正常传输拦腰截断 |
| 入房前的 hello | 16 KiB | — | hello 只有几百字节 |
| 资源响应 | 7 MiB | — | 桌面端的资源响应是一帧 base64 文本，中转读前 64 字节判断是不是它，是才整帧收下 |
| 建房频率 | 每个来源每分钟 30 次 | — | 同前 |

桌面端与手机之间的大数据分片、确认窗口和文件上传是两端之间的协议（「wire 2」），中转不参与、
也不需要认识它们，见 [ADR-0028](../../docs/adr/0028-sync-link-streams-large-data.md)。

### 版本兼容与升级顺序

`/health` 的 `version` 为 `2` 表示已是边收边转的中转。三端可以任意顺序升级：

- **新中转 + 旧桌面/旧手机**：帧格式不变，旧客户端照常工作；超过 8 MiB 的整帧和手机的分片消息
  不再断线。旧版手机 App 的心跳只认 pong，慢网络上一份大转录仍可能被它误判为断线——这一条要
  更新手机 App 才能解决。
- **旧中转 + 新桌面/新手机**：两端协商出 wire 2 后，大数据全部拆成 ≤ 256 KiB 的帧，且在途数据
  受确认窗口限制，所以旧中转的 8 MiB 上限和缺少背压都碰不到。手机读中转的 `/health`，认不出
  version 2 时把上行改成 48 KiB 一份、每份等发送缓冲清空再发，Chromium 就不会把它拆成延续帧。
  仍建议尽早升级中转：旧中转无法正确转发旧版手机 App 发出的分片消息，且那种限速把上行限在约
  12 MB/s。

一个房间最多两个人。第三个连进来会被拒（`room-full`）——房间号是从令牌派生的，出现第三个
意味着令牌泄露了，此时把它挡在外面比让它挤掉谁更合适。

0.9.0 的桌面端使用 `role: "desktop"` 并携带 `assetKey: SHA256("lyra-assets\0" + room)`；手机使用
`role: "mobile"`。旧 `host`/`guest` 角色仍兼容。`/app/<asset-key>/` 仅转发对应桌面 renderer
资源，接纳连接前会验证资源 capability 属于该房间，防止其他房间覆盖或抢占资源地址。资源地址
不能反推出会话房间号。该资源协议在 0.9.0 首次发布，开发版的旧派生规则不兼容，需同时更新三端。

## 跑起来

```bash
node packages/relay/server.mjs           # 默认 :8787
PORT=9000 node packages/relay/server.mjs
```

无依赖，单文件，Node 18.17+ 即可。生产环境建议放在 nginx/caddy 后面套 TLS，然后在桌面端填
`wss://你的域名`。
