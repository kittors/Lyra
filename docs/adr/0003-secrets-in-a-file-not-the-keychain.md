# ADR-0003：密钥存加密文件，不用系统钥匙串

- 状态：已采纳
- 日期：2026-09-03（追记）
- 相关：`packages/core/src/config/vault.ts`

## 背景

API key 和代码托管的令牌总得存在某处。显而易见的地方是 `safeStorage`——macOS 钥匙串、Windows
DPAPI、Linux keyring——而那也确实是这些令牌最初待的地方。

在 macOS 上它的代价比买到的多，原因很具体：这个应用的构建是 ad-hoc 签名的，所以它的
designated requirement 是自己可执行文件的哈希。钥匙串条目的访问控制记的正是这个 requirement。
每次发版都是一个新的构建，于是每次发版都有一个新哈希，于是在 macOS 看来**每个版本都是另一个
应用在要别人的密钥**。

表现出来就是：每次更新之后要重新登录 GitHub，还附带一个钥匙串弹窗。

## 决定

密钥存在 `~/.lyra/` 下的一个 AES-256-GCM 加密文件里，权限 0600。

## 后果

**挡住的**：`settings.json` 是会到处跑的——同步、在机器之间复制、粘进 bug 报告——而它曾经是
0644 并且里面就是明文的 API key。现在没有任何密钥在会被分享的文件里，全部是 0600。

**没挡住的，而且设置页明说了**：密钥就在密文旁边。任何能读你 home 目录的东西两个都能读到。
这是一个比钥匙串小的承诺，所以它被写出来，而不是含糊过去。

Windows 和 Linux 本来不受这个问题影响（DPAPI 认用户账号，keyring 认应用名），所以这实际上是
macOS 在为另外两个平台白拿的保证付钱。

## 什么时候该重新考虑

有了 Developer ID 签名之后。那时 designated requirement 认的是证书而不是可执行文件的哈希，
钥匙串条目跨版本就稳定了。改动是一行——`key()` 从哪里拿字节——文件格式本身不关心。

前提是买 Apple 开发者账号并做公证，那是产品决定，不是技术决定。
