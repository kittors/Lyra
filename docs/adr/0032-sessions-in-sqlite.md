# ADR-0032：会话存进一个 SQLite 库，流式回复边写边落盘，删会话不删账，旧日志导入一次

- 状态：已采纳
- 日期：2026-10-06
- 相关：`packages/core/src/session/{db,store,storage,types,apply-record,replay-records,spend,partial,legacy-jsonl}.ts`；
  `packages/core/src/runtime/session-log.ts`（`PartialWriter` 接在 `message_start` / `message_update` 上）；
  desktop `electron/usage-scan.ts`、`electron/usage-cache.ts`、`electron/session-cleanup.ts`、`electron/main.ts`（打不开就报路径）；
  `scripts/session-dump.ts`。移植自 wJiaaa/Lyra 的 91e57b7a（它的 ADR-0032），导入旧日志是这边加的

## 背景

会话原来是 `~/.lyra/sessions/<projectId>/<id>.jsonl` 加一份 `index.json` 索引，旁边还有 `<id>.display.json`
缓存展示结果。几处毛病都出在「一份事实存了好几份」上：

- 索引要整份重写，和删除、重建、新建之间反复出过竞态（新建的会话不在列表里、删掉的会话被一次更新写回来），
  每一种都靠一条写队列和一条专门的测试守着。
- 回复只在 `message_end` 才写进日志。进程在流式输出中途没了，这一轮已经收到的几分钟输出全部丢失。
- 用量页从会话日志里汇总花销，删掉一条会话，它花过的钱也从总额里消失，设置页的数字就对不上服务商的账单了。
- 移动会话要把文件在两个目录之间搬，搬一半失败时两边的状态都得处理。

fork 那边已经换成了 SQLite（参考了 maka 和 ZCode），这里把它搬过来。和 fork 不同的是：它那时还没上线，
旧数据不迁移；Lyra 已经发过很多版，每个人的全部历史都在那些 `.jsonl` 里，所以必须导入。

## 决定

1. **一个库：`~/.lyra/sessions/sessions.db`。** 用 Node 自带的 `node:sqlite`（Electron 43 / Node 24 都有），
   不加依赖。`sessions`（每条会话一行，带当前 meta）、`records`（只追加的记录，`(session_id, seq)` 唯一）、
   `partials` / `partial_chunks`（正在流式输出的回复）、`spend`（每一次计费调用），加一张 `info` 记库的标识和导入标记。
   表结构的版本记在 `user_version`。
2. **每条记录连同它引起的一切在一个事务里写完。** 读当前 meta、算下一个 `seq`、插记录、更新 `sessions` 行、
   写花销、清掉已提交回复的流式残留，都在 `BEGIN IMMEDIATE` 里。调用方手里的 meta 过期了也没关系，事务里读到的
   才算。原来的写队列和索引重建整个没有了。会话已经被删掉时，迟到的写入什么都不提交、`append` 返回 `null`，
   桌面端的观察层据此不再广播，删掉的会话不会被一次迟到的标题或用量写回侧边栏。
3. **历史不改写。** 撤回仍然是一条 `truncate` 记录，读的时候跳过被作废的尾巴；手机 `?since=N` 的增量契约不变。
4. **流式回复边写边落盘。** 第一段立刻写，之后每 80ms 或攒够 8KB 写一次，只写每个块新增的尾巴。回复提交时在同一个
   事务里删掉残留。读到一段写入者已经不在的残留（进程死了；最后一次写入早于本次开机；本进程里已经没人在写），
   就把它当成「按了停止」的那条回复提交进去（`stopReason: "aborted"`），只留文字和思考，丢掉写了一半的工具调用。
   一轮在流式中途抛了异常，轮次结束时就地按同样的规则提交（`settleOrphan`）。正常退出时先同步写完还没写出的那一批，
   再关库。每次开始流式都生成一个 token，追加、丢弃、提交时的清理都只认它，旧写入者碰不到新的那一段。
5. **花销单独一张表，删会话不动它。** `spend` 没有外键；分叉复制过来的历史标记 `copy`，不重复计费；压缩和撤回各记
   一行边界。用量页按 `spend.id` 增量读、一页最多 5000 行，缓存里记下库的标识：库被挪走重建或从备份恢复后行号
   从头编，标识对不上就从头读。
6. **打不开就报路径，不自动重建。** 打不开可能只是被锁、或者同步盘拷了一半，自动重建会把所有会话清空。桌面端启动时
   先试开一次，打不开就弹窗说出路径和原因然后退出；库是更新版本的 Lyra 写的（降级）也走这条。
7. **删除后立刻归还空间。** `auto_vacuum = INCREMENTAL`，每次删除后跑 `incremental_vacuum` 再 `wal_checkpoint(TRUNCATE)`，
   平时用 `journal_size_limit` 限住 WAL。fork 实测：320MB 约 0.5s，1GB 约 1.7s；分步做最长停顿仍有 150–670ms、
   总耗时变成三倍，所以一次做完。
8. **旧日志导入一次。** 库第一次被打开、任何读写之前（`ready()`），把旧日志一份一份读进来：文件在事务外读，
   每个会话在自己的事务里整份写入，`info` 里记一笔就再也不导——之后重导一遍会把这期间删掉的会话都带回来。
   - **有 `index.json` 就只导它列出的会话，按它的顺序，用它的 `updatedAt`。** 旧侧栏就是照它画的，所以：
     索引里有、日志没有的会话也导进来，照索引的样子、不带记录（旧侧栏照样列着它）；日志的 meta 行坏了，用索引里
     那份顶上。删除是先删日志再删索引项、删日志失败被吞掉，所以不在索引里的日志对旧存储来说不是会话（清理页的
     测试原话是「但它不是一条会话」），导进来就是把删过的会话带回来。时间并列时列表按导入先后排，和旧索引的
     稳定排序一致。没有索引（缺失或坏了）时导入全部日志，旧存储那时也是扫全部日志重建的。
   - **不是会话的日志，花过的钱照记。** 不在索引里的、没有 meta 记录的（手写的固件就是这样）、整份导不进来的，
     都不变成会话，但它们的计费调用写进 `spend`：旧用量页是把目录里所有日志加起来的，而删会话本来就不再从
     总额里扣钱。它们没有记录，所以不算进按天的活跃数。
   - `seq` 原样保留（手机手里拿着它）；只有旧日志里乱序或重号的才接着前一条重新编号，指向那一段的 `truncate`
     跟着改到新编号的同一位置。meta、消息条数、用量按旧存储读回会话时的算法从记录算出来；花销照记录写进 `spend`，
     用量页的历史不断。
   - 解析不了的行照旧跳过。没有用量、或用量里缺 `cost` 的回复按零用量导入，内容照样显示——旧存储也是照样显示、
     只在求和时跳过它们，手写的日志（e2e 的固件就是）大多是这样；起初把它们当成坏记录丢掉，带代码块的回复
     就从对话里消失了。真正读不出东西的记录（`event` 是 `null` 之类）只丢这一条；一份日志整份导不进来只跳过
     这一份并打一条警告。任何一份旧日志都不能让应用打不开。
   - 原文件留在原地当备份，不再读。
   - 在一份真实历史的副本上实测（2026-10-06，33 个会话，目录 70MB，其中日志 23MB、展示缓存 48MB）：导入发生在
     第一次列会话时，连同列出共 0.28s；33 个会话的标题、归档、条数、用量、`seq`、消息内容、展示内容、压缩点、
     命令记录、记录数逐项和旧存储读出来的一致，侧栏顺序一致；用量页 1910 次回复、$22.454076、13 个桶全部一致。
9. **按天的活跃数按记录写入的时刻算，不按消息自己的时间戳。** 时间戳只在正文里，逐条解析在同一份历史上要 32ms，
   按写入时刻是 2.9ms，而且随历史线性涨；换来的是 3933 条里有 1 条（跨午夜写完的回复）挪到第二天。它的 token
   仍记在开始那天。

## 没有做的

- **不删 fork 删掉的那些兼容逻辑。** fork 顺手删了设置迁移、旧名字、旧钥匙串等「上线前的兼容」；这边那些都发给过
  用户，一条不动。
- **不搬「删除先占位」。** fork 让所有删除先把会话标成「删除中」再停、再删。这边的删除入口照旧先 `disposeSession`
  停掉会话、再删库里的行，删后迟到的写入由第二条兜住。真遇到「停和删之间有新请求把会话拉起来」再搬。
- **不删旧文件。** 导入后旧日志、`index.json` 和展示缓存都还在盘上，删掉一条会话也不删它的旧日志。要不要在导入后
  清掉展示缓存、删会话时连带删掉它的旧日志，牵涉删用户的文件，留给人定。
- **不开第二个连接、不放到工作线程。** `node:sqlite` 是同步 API，会占住主进程。fork 实测一次追加 p50 0.04ms、
  p99 0.26ms；5000 条消息的会话整条载入约 22ms。等有真实会话量到卡顿再挪。

## 后果

- 用 `cat`、`grep` 直接看会话不行了，用 `pnpm dump:session <id>` 倒出来，形状和以前的 `.jsonl` 一样。
- `~/.lyra` 不能在应用开着的时候放进同步盘：库旁边的 `-wal` 文件和库本体必须一起拷。换机器前先退出应用。
- 按天的「活跃会话数」来自记录表，删掉的会话不再算活跃；花销来自 `spend`，删掉的会话照样算。两者口径不同是有意的。
- `pnpm audit:sessions` 读的是库；在还没被新版本打开过的目录上跑，它会先做一次和应用第一次启动一样的导入。
- 单测和 e2e 的固件仍然写 `.jsonl`：e2e 在应用启动前写好，第一次启动时导入；时间和顺序以固件写的 `index.json` 为准。
  两处固件跟着改了：用量面板的 40 份日志原来没有 meta 行，导进来只剩花销、没有活跃数，那几条断言在空页面上
  照样绿（只查了标签在不在），现在每份都带 meta 行；定时任务那条原来在项目目录的位置放一个文件让建会话失败，
  一个库没有按项目的目录可以弄坏，改成测试进程占住库的写锁。
- 删掉的会话，内容还留在它的旧日志和展示缓存里（见「没有做的」第三条）。
- 导入标记记在库里。库坏了被移走、Lyra 新建一个之后，旧日志会再导入一次：升级前的历史回来了，升级后删掉的
  那些也一起回来；升级后的对话在移走的那个库里。

## 什么时候该重新考虑

- 有人的历史大到导入要好几秒：第一次启动会停在加载中，那时要给导入一个进度，或者挪到后台。
- 主进程在打开长会话时明显卡顿：把读挪到工作线程或第二个连接。
- 发过足够多版、没人还留着 `.jsonl` 时：删掉 `legacy-jsonl.ts`，连同 `projectId` 这类只为旧存储留着的参数。
