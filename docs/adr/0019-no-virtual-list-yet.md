# ADR-0019：长会话不上虚拟列表——量过了，不需要

- 状态：已采纳
- 日期：2026-09-03
- 相关：`packages/desktop/e2e/transcript-perf.ts`

## 背景

一个八千多条消息的会话，滚动和拖拽会不会卡，是「要不要上虚拟列表」这个问题的全部。
虚拟列表不是免费的：它换掉滚动容器，与 `useFollowBottom`（440 行，刚做过一轮）耦合最紧，
而且会让「⌘F 搜得到没渲染的那一屏吗」这类问题重新变成问题。

计划里为此写了决策规则，而不是直接排期：**先量，p95 超过一帧（16.7ms）才做。**

## 决定

不做。量出来没超。

`transcript-perf.ts` 在这台机器上最大的真实会话上跑——8948 条消息，8,618 个 DOM 元素，
项目是 Lyra 自己：

| 手势 | 帧数 | p50 | p95 | 最长 |
| --- | --- | --- | --- | --- |
| 拖面板边界 | 44 | 16.7 | 17.6 | 18.1 |
| 搬面板穿过 dock | 74 | 16.7 | 18.4 | 316.1 |
| 拖侧边栏边缘 | 44 | 16.7 | 17.5 | 18.6 |
| 滚动会话 | 57 | 16.7 | 18.0 | 18.2 |
| 同上，但不渲染会话 | 44 | 16.7 | 18.1 | 18.4 |

倒数第二行和最后一行是这张表里最有说服力的一对：**把会话整个不渲染，滚动的 p95 是
18.1ms；渲染着是 18.0ms。** 会话内容对滚动开销的贡献在噪声里。虚拟列表要优化的正是这一项，
而这一项已经不在关键路径上了。

真正做了事的是 `content-visibility: auto` 加 `contain`——30 个助手行里 0 个被跳过（都在视口
附近），但浏览器仍然可以跳过屏幕外的绘制。加上「show earlier」的分页，长会话的成本已经被
按住了。

## 后果

**这条不是「以后再说」，是「量过了，当前不需要」。** 重新考虑的条件是明确的：同一个探针在
真实会话上跑出 p95 持续超过 16.7ms。

`搬面板穿过 dock` 那一列的 316ms 最长帧是一次性的适配开销（`data-dock-settling` 的样式重算，
3.9ms 那一行是它的分解），不是滚动成本，与虚拟列表无关。

**没有虚拟列表这件事本身也有价值**：⌘F 搜得到整个会话，打印和截长图拿得到全部内容，
辅助技术读得到没在视口里的消息。这些都是虚拟列表要专门补回来的东西。
