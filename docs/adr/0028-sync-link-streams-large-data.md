# ADR-0028：手机链路上的大数据按份传、带确认窗口，中转边收边转，文件走上传而不塞进消息

- 状态：已采纳
- 日期：2026-09-27
- 相关：`packages/relay/server.mjs`；desktop `electron/sync-wire.ts`（分份与窗口）、`electron/sync-uploads.ts`（上传落盘与续传）、`electron/sync-server.ts`、`electron/sync-relay.ts`、`electron/prompt-input.ts`（上传 id 换成路径）、`src/features/composer/attachments/phone-upload.ts`；mobile `src/bridge-wire.ts`（手机一侧的同一协议）、`src/bridge.ts`；量法 `packages/desktop/e2e/sync-large-probe.ts`、`packages/relay/test/relay-bench.ts`

## 背景

用户转述的反馈：「中继服务器……对话数据一大就容易卡慢以及出现问题，移动端传大文件也是，很容易崩。」

先量再改。真实桌面应用（临时 profile，拷入本机最大的真实会话并按 ×6 复制出 4164 条消息、转录
1400 万字符）、本地起的中转、Chromium 里跑的真实手机 bridge 与 renderer；手机一侧 4 倍 CPU 降速，
手机那一段网络用限速代理（局域网 20 MB/s；中转下行 6 MB/s、上行 3 MB/s、单程 30 ms）。
量到的问题，每一条都能单独让链路断掉：

| 现象 | 根因 |
| --- | --- |
| 经中转打开大会话断线，重连后又去读同一份转录，再断 | 中转把帧整帧攒下再转，超过 8 MiB 就断开桌面端；手机恢复时重读当前会话，于是循环 |
| 经中转从 Android 发任何大于约 128 KiB 的消息都断线（一张截图就够） | Chromium 把大消息拆成延续帧；中转给每一片都置了 FIN，桌面端收到截断的 JSON 和无主的延续帧，按协议错误关闭 |
| 中转转 4 MB 的消息 RSS 到 213 MB，16 MB 到 491 MB | 每来一块 TCP 数据就把整个缓冲 `Buffer.concat` 一遍，复制量是帧长的平方 |
| 慢手机时中转内存一路涨（64 × 1 MiB 到 258 MB） | 写对端从不看返回值，没有背压 |
| 手机被杀掉后同一部手机重连被拒 `role-full` | HTTP server 交出的升级 socket 是半开的，对端只发 FIN 时 `close` 不来，死成员一直占着位 |
| 局域网发 100 MB 日志：WebView 堆 1.3 GB，桌面端拒收 | 附件整个读进 WebView、base64/文本塞进 prompt、一帧发出；桌面端 `ws` 默认上限 100 MiB |
| 手机发任何附件都失败：「发送失败：Invalid attachment path」 | 手机 bridge 对未知方法的兜底返回一个 promise，输入框把 `pathForDrop` 的这个返回值当路径发出，桌面端整条拒收 |
| 大转录传输中途被自己的心跳判死 | 心跳只认 pong，而 pong 排在大帧后面；RPC 超时又是 20 秒的总时长 |

## 决定

1. **中转边收边转。** 帧头一到就转，载荷来一块转一块，FIN 与 opcode 原样保留（分片消息仍是一条
   消息）。对端待写超过 1 MiB 就暂停读发送方，`drain` 再恢复；60 秒不收一个字节的接收方按已断开
   处理。中转自己的帧只在边界插入（数据帧等分片消息结束，pong 等当前帧结束）；一端在一帧或一条
   分片消息的中途离开，另一端直接断开重连，而不是被喂半截帧。半关闭即离开，另开 TCP keepalive。
   单帧上限从「8 MiB，因为要攒」改成「256 MiB，只是长度字段的合理性检查」；每连接累计从 1 GiB
   改为 8 GiB（手机现在能传最大 2 GiB 的文件）；都可用环境变量调。`/health` 报 `version: 2`。
2. **两端协商 wire 2，大消息按份传。** 桌面端的 hello 加 `wire: 2` 与 `maxUpload`；手机在链路可用时
   先说 `{"type":"wire","version":2,"inflate":["deflate-raw"]}`，再发任何排队的调用。双方都说了之后，
   超过阈值的消息先发一条 `stream` 通告（大小、是否压缩、答的是哪个调用），再发二进制分份
   `[kind u8][sid u32][offset f64][bytes]`，收方每份回 `ack`。发送方在途不超过 1 MiB——无论中间是
   新中转、旧中转还是局域网，内存和延迟都以这个窗口为界。
   - 桌面→手机每份 256 KiB（`ws` 不会拆帧），对能解压的手机先 `deflate-raw`（真实转录压到约 1/4）。
   - 手机→桌面：直连和 version 2 的中转每份 256 KiB（`ws` 与新中转都能把分片拼回去）；经一个不能
     确认是 version 2 的中转（手机读它自己的 `/health`）时每份 48 KiB，且等 `bufferedAmount` 归零再发
     下一份：实测 Chromium 在发送繁忙时连 64 KiB 的消息也会拆（400 条拆了 387 条），一次只让一份在
     管道里则 500 次一次不拆。这是新手机能继续走旧中转的前提；只在需要时这样做，因为它把上行限在
     约 12 MB/s。
   - 推送（agent 事件等）保序：一条大推送在最后一份写出前，后面的推送排队；调用的答复彼此独立，
     小的不等大的。手机侧解压是异步的，之后到的消息等它解完再投递。
   - 任何一帧都证明链路活着，不只 pong；调用的 20 秒超时改为「20 秒没有进展」，答复的每一份都续期。
3. **手机的大文件走上传，不进消息。** `files.upload(file)`（手机 bridge 提供，不是 IPC 方法，契约不变）
   从 WebView 自己的 `File` 按份读——那是磁盘背书的对象，不会整个进内存，也不经过 RN 与 WebView
   之间的桥——发 `upload_begin`，按份发 `kind 2`，桌面端写入 `<lyra home>/uploads/<id>.part`、写盘后
   才回 `upload_ack`，满了改名为 `<id>/<文件名>` 回 `upload_done`（带路径）。断线后手机带着 `resume: <id>`
   重问，从桌面端盘上的长度续传；超过 5 分钟连不回来就失败并说明原因。上限 2 GB，写在 hello 里，手机
   先拦；磁盘剩余不足 512 MB 余量时拒收。未完成的一天后清理，完成的三十天后清理。
   - prompt 里附件只带上传 id；桌面端 `prompt-input.ts` 把它换成自己写的那个路径，这是远端附件拿到
     `path`（也就是这一轮可读许可）的唯一途径。编辑重发时带回的路径，只有正好是上传仓库里已完成的
     文件才认。id 是 128 位随机数，路径由桌面端决定，文件名只取基名。
   - 输入框在手机上：大于 4 MiB 的图片、大于 256 KiB 的文本、以及手机抽不出字的一切（PDF、压缩包、
     视频）走上传，正文里写一句文件在桌面端的位置，agent 用自己的工具去读；小图和短文本照旧内联。
     旧版手机 App 答不了上传时退回原样，但不再读超过 16 MiB 的文件。

## 量出来的前后

同一脚本（`e2e/sync-large-probe.ts`）、同一份数据、同一组限速；「前」是改动前的工作区（仅补了
`pathForDrop` 那一行，否则所有附件在任何大小下都发不出去，量不出大小的影响）。

| 场景 | 改前 | 改后 |
| --- | --- | --- |
| 局域网打开 4164 条消息的会话：首屏 / 调用 / 最长任务 | 1933 ms / 1674 ms / 579 ms | 848 ms / 714 ms / 188 ms |
| 中转打开同一会话 | 断线，之后重连循环，其他操作一并失败 | 1147 ms，0 次断线 |
| 局域网发 20 MB 图片 / 20 MB 日志 | 成功 8.5 s / 4.3 s，手机堆 231 / 373 MB | 成功 1.1 s / 1.1 s，手机堆 60 / 47 MB |
| 局域网发 100 MB / 300 MB 日志 | 断线失败，手机堆 1289 / 1638 MB | 成功 5.1 s / 15.1 s（贴着 20 MB/s 限速），手机堆 ≤ 91 MB |
| 中转发 20 / 100 / 300 MB | 全部断线失败（300 MB 时手机堆 2.4 GB、页面无响应） | 全部成功，6.8 s / 33.4 s / 100.3 s（贴着 3 MB/s 上行），中转 RSS ≤ 48 MB |
| 新两端经**旧**中转：打开同一会话 / 发 20 MB / 100 MB | —— | 1330 ms / 7.0 s / 33.6 s，0 次断线（手机按 48 KiB 限速分份） |
| 中转转发 16 MB / 64 MB 单帧（基准） | 断线，RSS 491 / 539 MB | 完整送达，RSS 82 / 105 MB；256 MB 也送达，134 MB |
| 中转转发慢读者 64 × 1 MiB | RSS 258 MB | 80 MB |

手机上的时间花在哪：renderer 本来就只挂最后几轮（`WINDOW_TURNS`），渲染首屏在 4 倍降速下约
130–260 ms，与会话长短基本无关；改前的大头是 1570 万字节的一帧在网络上的时间和手机上解析它
（202 ms），以及经中转时直接断线。桌面端这一侧读显示缓存 152 ms、序列化 19 ms、压缩 75 ms。

## 没有做的

- **转录不分页。** 量过：首屏渲染已被既有的窗口化限住，剩下的是传输与解析，压缩与分份已经把它降到
  原来的 1/4 上下。真正分页要改 store 里按下标寻址的一切（编辑重发、撤回、分叉都用消息下标），
  代价与风险不成比例；等出现压缩后仍然过大的会话（数十 MB 的转录）再做「先尾后头」。
- **不在中转做带宽限速。** 需要时在前面的反代上做，它能限速而不是断开。
- **上传进度的界面。** 手机界面归另一条工作线；数据已经给出：`sync.onTransfer(handler)` 与 window
  上的 `lyra:transfer` 事件（`SyncTransfer`：id、kind、direction、name、done、total、state、error），
  `files.upload(file, { onProgress, signal })` 可取消。上传完成前附件不进草稿，所以发不出一条指着
  未完成文件的消息。
- **iOS WKWebView 是否拆帧没有实测。** 新中转无论如何都能正确转发分片；旧中转下 iOS 的行为未验证。
- **不做端到端加密。** 同 ADR-0002：中转可信，传输安全来自 TLS。

## 兼容与升级顺序

| 组合 | 结果 |
| --- | --- |
| 新桌面 + 新手机 | wire 2：分份、窗口、压缩、上传 |
| 新桌面 + 旧手机 App | 旧手机从不说 `wire`，桌面端发的与改前逐字节相同（hello 只多两个它忽略的字段）；新 renderer 调 `files.upload` 得到兜底的 null，退回内联，且不读超过 16 MiB 的文件 |
| 旧桌面 + 新手机 App | 旧桌面不带 `wire` 的 hello：手机不发任何二进制帧，大调用照旧一帧，上传答 null；手机先发的那条 `wire` 被旧桌面当作无 id 的消息丢弃 |
| 新两端 + 旧中转 | 大数据都是 ≤ 256 KiB 的帧、在途 ≤ 1 MiB，碰不到旧中转的 8 MiB 上限与无背压；手机从 `/health` 认出旧中转，按 Chromium 不拆的方式发（实测见上表） |
| 旧两端 + 新中转 | 帧格式不变；8 MiB 以上的整帧与分片消息不再断线 |

三端可以任意顺序升级，不需要重新配对。建议先升级中转（它独立部署，旧手机 App 的分片问题只有它能
修），再发桌面与手机。

  `mobile/test/bridge-wire.test.ts`。
- 协议面多了一套：两份实现（TS 与 WebView 里的字符串脚本），由 `sync-link.test.ts` 把两者接在一起跑。

- 契约方法数不变：`files.upload`、`sync.onTransfer`、`sync.capabilities` 是手机 bridge 自己的，
  在 `ipc-types.ts` 里标为可选。
