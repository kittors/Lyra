# ADR-0024：子代理停在检查点，不停在终点——上下文留着，可以续跑

- 状态：已采纳
- 日期：2026-09-24
- 相关：`packages/core/src/runtime/sub-agent.ts`、`runtime/sub-agents.ts`、`runtime/continuation.ts`、`tools/task.ts`、`agent/loop.ts`（`AgentRunResult.view`）、`agents-builtin.ts`（`maxTurns`）、`capability/providers/native.ts`、desktop `features/subagents/SubAgentPanel.tsx`、`features/subagents/way-back.ts`

## 背景

用户反馈原话：「子代理设置了 60 步，很容易跑满就导致啥活都没干好……主会话以及重开三个子代理，
都是 60 步，最后主会话看不下去了，自己做了。这不是白烧 token 嘛」。

顺着代码查下来是一条五环的链，每一环都在把已经花掉的钱扔掉：

1. **60 是拍的。** 8 月 12 日引入子代理时直接写了 `maxTurns: 60`，9 月 9 日提成常量时补的理由是
   「可能同时有十来个在跑」。而并发此后由派发闸门管着（默认 4 个、上限 8 个），这个数没有再跟着改。
   它也不是量出来的：同样 60 轮，不同模型每轮做的事能差一倍（见
   [agent-cost-and-stopping.md](../architecture/agent-cost-and-stopping.md) C3）。
2. **到 60 就停，停了就扔。** 只有带输出格式的子代理（explore/review/verify）有补交那一轮；默认的
   `general` 交回的是「停下前最后说的那句话」，读文件读到一半被截断的，多半是「让我再看看 xxx」。
   上下文随着这一次运行结束整个丢掉。
3. **没有续跑的路。** `task` 只有 `description`/`prompt`/`subagent_type`，结果里不带 id；登记簿的
   `steer` 只对运行中的有效；面板上的「重新派发」起草的是「再派一个同样的」——从零开始。
4. **给父模型的话是「把任务拆小再派一次」。** 它照做了：新派的那个从零开始，读同样的文件，又跑满。
   反馈里重开的三个就是这么来的。
5. **跑满的那一种在面板上没有出路。** 它的状态是 `done` + `incomplete`，「重新派发」只挂在
   `failed`/`aborted` 上。

对照了三家（读源码或官方文档，不是摘要）：

| | 默认上限 | 到上限时 | 能否接着跑 |
| --- | --- | --- | --- |
| Claude Code | 不设（`maxTurns` 可选） | 输出标「部分」，注明可续 | 能，按 id 发消息，保留全部历史，能接着读原来那次预热的缓存 |
| opencode | 不设（`agent.steps ?? Infinity`） | 收掉工具，强制写「做了什么/剩什么/下一步」 | 能，`task_id` 续同一个子会话 |
| oh-my-pi | 软预算 200（侦察类 100） | 先提醒收尾，1.5 倍时强制交付，挂起 | 能，结果里明说「可续，别重做」，重启后冷恢复 |

四家里只有我们会把停下的子代理整个扔掉。

## 决定

**轮数只决定「多久停下来看一眼」，不决定「最多干多少活」；停下来的子代理是暂停，不是作废。**

1. **检查点。** `SUB_AGENT_CHECKPOINT_TURNS = 60`，按定义可改（agent 文件里的 `max-turns`）。
2. **检查点上看清单。** 它自己的清单在往前推就接着跑，连着两段一项没完成、或者没写清单，就停。判据直接
   复用主会话的续跑链 `continueWhileWorkRemains`——它在 5 小时 $10.72 那次事故上校准过，不是另起
   一个「它是不是在瞎忙」的猜测（`repetition.ts` 顶上那两次误伤就是这么来的）。
3. **停下时，所有类型都交接。** 带输出格式的照旧按自己的格式交；没有的用 `HANDOFF_SCHEMA`
   （`summary`/`remaining`/`next`）。讨交接那一轮只剩 `yield` 一个工具。
4. **不扔上下文。** 循环把模型最后看到的那份历史交回来（`AgentRunResult.view`，压缩、裁剪之后的），
   登记簿把它和子代理自己的状态图（清单、读过哪些文件、裁剪器）一起留下（`keep`）。讨交接那一轮不
   算进去：续跑时它从交代之前的地方接着干。
5. **续跑。** `task` 多一个 `resume`：同一个 id 重新打开（`reopen`），请求 = 留下的历史 + 一句新话，
   前缀跟它停下前最后一个请求逐字相同。只能续自己派出去的；认全名，也认冒号后那一截。
6. **父模型听到的话。** 面板和父模型都看到「它还没做完，上下文还在，可以接着跑」；只说给模型的那一
   段在 `task` 的结果末尾：「传 `resume: "<id>"`，**不要**重新派一个」。做完的也给 id，追问一句不用
   从头查。人在面板上按停的，明说「除非用户要求，不要续跑它」。
7. **面板。** `wayBack()` 决定出路：上下文在、又没做完 → 「接着跑」（草稿进主输入框，带 id）；上下文
   不在才是「重新派发」。

## 没有做的

- **不把 60 换成另一个数。** 换个数还是一刀切，问题不在数上，在「到了就扔」。
- **不发明新的进展判据。** 没写清单的子代理到检查点就交接，由父模型决定续不续——拿不准的交给
  人（这里是父模型），不让循环替它决定。
- **不从面板直接续跑。** 一个工作区一个执行者；续跑的结论要回到父模型那里才有用。和「重新派发」
  同一个间接法：落成输入框里的草稿，人读过再发。
- **不做跨重启续跑。** 登记簿在内存里，重启后上下文就没了，`lookupResumable` 会明说「重新派一个，
  把它交回的结论带上」。子代理的消息已经落盘（`subagent_message`），将来要做可以从日志重建，但要
  把压缩边界和状态图也落盘，这次不做。
- **不在对话里念账单。**

## 后果

实测，全部在 `~/Desktop/子代理续跑测试/`：

- **真实模型，续跑 vs 从零重派**（`gemini-3.8-flash-high`，同一件只读梳理任务，先逼它在 3 轮停下）：

  | | 请求 | read | 重读停下前读过的 | 输入 token（未缓存＋缓存） | 耗时 |
  | --- | --- | --- | --- | --- | --- |
  | 续跑（同一个 id） | 6 | 5 | 0 | 107,823 | 24.9s |
  | 从零重派（prompt 里带着交接） | 22 | 20 | 5 | 417,742 | 104.4s |

  重派的那个即使拿到了交接，还是把读过的文件读了一遍又一遍。续跑只花了约四分之一。
- **截包**：续跑后第一个请求与停下前最后一个正常请求，`input` 前 8 项逐字节相同，系统提示、工具、
  其余参数都相同。这次中转没有在续跑的第一个请求上命中缓存，同一段里后面的请求命中了——缓存命不
  命中是供应商的事，前缀对不对是我们的事，后者已经对了。
- **真实模型当主会话**：scout 停在检查点之后，主模型调的是 `task` + `resume`，没有重派。
- **真窗口**（假模型走真适配器）14/14：面板标出「没跑完」、给「接着跑」、草稿带 id、主 Agent 续跑后
  名单上还是那一个、续上之后没有重读。

代价：

- 登记簿多留一份模型视图（消息对象跟转录共用，额外的只是数组），最多 24 个。
- 没有输出格式的子代理到检查点多一轮讨交接；那一轮工具表只有 `yield`，前缀变了，缓存不命中。
- `SubAgentSummary` 多了 `resumable`、`resumes` 两个字段；`subagent` 事件多了 `resumed`。
