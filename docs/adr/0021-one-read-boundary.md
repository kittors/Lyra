# ADR-0021：读取边界只有一条，越界读要经过人

- 状态：已采纳
- 日期：2026-09-20
- 相关：`packages/core/src/tools/read-access.ts`、`tools/paths.ts`、`tools/bash.ts`、`sandbox/policy.ts`
- 延续：[ADR-0004](0004-sandbox-fails-closed.md)（拿不到约束就拒绝）

## 背景

「这个文件能不能读」在这个应用里曾经有两个互不相干的答案。

文件工具问的是**路径在不在 cwd 下**：`resolveWorkspacePath` 不在就抛
`Path escapes the workspace root`。`bash` 问的是**命令改不改文件**：沙箱模式只
`(deny file-write*)`，读从不过问；而 `isReadOnlyCommand` 那张只读表（`cat`、`head`、`grep`、
`wc`）命中就根本不发起审批。

于是同一个路径，`read` 拒绝、`cat` 放行，**任何权限模式下都如此**，包括最严格的 `ask`。

两个后果都发生了，而且都不是假设：

- **密钥规则被架空。** `SECRET_PATH` 判定 `cat ~/.ssh/id_ed25519` 为 risky，但它活在
  `assessCommand` 里，而只读表在它前面短路。回放本机 303 个真实会话，私钥被这样读过 12 次，
  一次窗都没弹过。2026-09-12 的审计把这条列为 H2，修复记录标了 ✅——规则写对了，位置错了。
- **模型被教会绕路。** 提示词里当时没有任何一句提到这条边界，模型读到的不是「这是规则」而是
  「这个工具坏了」，于是换 `cat`，而那条路真的通。用户看到的就是「读另一个项目说没权限，
  然后它用 bash 去绕」。

## 决定

**建立「读取授权」这一个概念，所有读取入口都问它。** 判定在 `read-access.ts`：

- `allow`：工作区、scratch、已安装技能、用户拖进来的附件、以及工具链要读的系统目录和临时区。
- `ask`：其余工作区外的路径，授权范围是**所属项目**（向上走到 git 仓库根）；凭据类路径无论
  在哪都问，授权范围是**文件本身**。

三条随之而来的决定：

**一、跨界读改成「问」，不再是「拒」。** 硬拒加上 bash 能绕是最坏的组合：安全没拿到，体验也
没拿到，还逼出绕路。`paths.ts` 里记着同一个教训的上一次——硬拒把模型逼去用 MCP filesystem
server。问一次、批准后记住整个项目，边界才是真的（人在环），用户也才有正当出路。

**二、`bash` 在只读表之前问同一个判定。** 这个顺序就是修复本身。那张表回答的是「这条命令改不改
东西」，对 `cat` 永远答「不改」，无论 `cat` 指向哪里。

**三、写这一侧原样不动。** `write`/`edit` 仍然只在工作区内，不提供「问一下就能写出去」。附件是
「给你看」，从来不是「可以改」，所以 `resolveWorkspacePath` 上那两个死参数删掉了。

## 没有做的

**没有在内核层封读。** 实测 `(deny file-read* (subpath ~/.ssh))` 确实封得死、工具链也不碎，
但 ssh 读不了 `known_hosts` 就连不上，`git push` 直接挂。这一层的代价大于收益。

因此命令行的路径提取是**字面的**：`$DIR/key`、glob、`$(…)` 一律不猜——猜会同时产生假放行和
假弹窗。它挡的是模型实际会写的形态，不是决心绕过的攻击者；后者要靠内核层，而那条路上面说了。
这是一个明确的限度，不是一个待补的洞。

**`full` 模式下读取不问。** `full` 就是「没有沙箱」，`cat` 在那个模式下从来畅通；让 `read` 也
畅通是**消除**不一致，不是放宽攻击面。

## 后果

**得到的**：「能不能读」有唯一答案，不因为换个工具而不同；密钥规则回到了会被问到的位置；
用户第一次有了正当的「让它看另一个项目」的路；模型不再有绕路的理由，提示词也明说了。

**付出的**：多了一类审批。拿 303 个真实会话、30173 次工具调用标定过——**中位数 0 次，平均
每会话 0.63 次，72.3% 的会话完全不弹**。这个预算由 `test/read-access.test.ts` 里的
「日常命令一次都不许问」守着。

**要小心的**：授权范围不是前缀授权。同一个 git 仓库内的文件会算出同一个范围，所以批准一次就
够；非 git 目录的深层子目录会各自成范围，要各问一次。做成前缀授权需要把已授权集合穿透到
`ToolContext`，收益有限，没做。

## 2026-09-21 补：一个项目可以不止一个文件夹

上面那句「授权范围是**所属项目**」当时只有一种读法，因为项目就是一个目录。现在不是了：
`ProjectEntry.folders` 让一个项目由几个源文件夹组成（应用仓库 + 接口仓库，或者旁边那份设计
稿），这是用户在「创建项目 / 编辑项目」里明说的。

这条边界跟着改了一处，只有一处：**`assessRead` 多认一组根**（`ReadAccessOptions.projectRoots`，
由 `config/project-roots.ts` 从 `settings.projects` 按 cwd 算出来，每轮读一次）。判定的其余部分
一个字没动——密钥仍然无论在哪都问，而且排在这组根**前面**：把一个文件夹加进项目说的是
「这是我要做的活」，不是「我放在里面的钥匙你随便读」。

**为什么必须动。** 不动的话这个功能是假的：用户配了第二个文件夹，模型每读一个文件弹一次
「读取当前项目之外的位置」——而那正是上面说的「逼出绕路」的处境，只是这次是我们自己造的。

**提示词也跟着说了。** 多出来的文件夹会列进系统提示，而且同一段里明写「这些文件夹只读，
`write`/`edit` 仍然只在工作目录内，这是规则不是故障」。理由还是上面那条：一条不说出口的规则
等于没有——正面说它能读，模型才会去读；正面说它不能写，模型才不会去 `sed`。

**写这一侧仍然原样不动。** 上面「决定」的第三条继续成立。人在文件面板里编辑第二个文件夹的
文件是可以的（那是主进程的 `allowedRoots`，走的是人的手），模型的 `write`/`edit` 不行。这两个
不是同一扇门，也不该是。
