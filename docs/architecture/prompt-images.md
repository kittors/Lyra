# 发给模型的图片：进来时缩一次，发出去时按预算带

代码在 `packages/core/src/images/`：`shrink.ts` 是一张图怎么缩（尺寸、格式、质量的全部决定），
`fit.ts` 和 `dimensions.ts` 是它用的纯规则，`codec.ts` 是宿主注入编解码的接缝，`fit-entry.ts` 是图进会话
那一刻的适配，`request-budget.ts` 和 `request-images.ts` 是每个请求带哪些图。两个编解码实现：桌面主进程的
`packages/desktop/electron/image-codec.ts`（`nativeImage`，macOS 上解不了的格式交给 `sips`），渲染进程的
`packages/desktop/src/lib/image-shrink.ts`（canvas）。

真窗口探针：`packages/desktop/e2e/image-shrink-probe.ts`（假 Anthropic 端点抓真实请求体），固定样本由
`e2e/image-samples.ts` 生成（10 张 4K 截图 + 3 张 4032×3024 照片，其中一张 HEIC）。

## 为什么要管

每一个请求都把整段历史重发一遍，图片也在里面——prompt cache 省的是供应商那边的计算，不是上行。改之前
在样本上量到的（`image-shrink-probe.ts 改前`）：

| | 改前 |
|---|---|
| 第 1 轮（13 张图） | 请求体 24.23 MB，原图原样：4K PNG 单张最大 6.8 MB |
| 第 3、4 轮（只多一句话） | 25.67 MB，每轮原样重发 |
| 15 KB/s 上行（用户的中转实测） | 每轮约 28 分钟 |
| `session-media` 落盘 | 19.27 MB |

还有两件更糟的：6.8 MB 那张超过 Bedrock 和旧版 API 的单图 5 MB（base64），HEIC 不是任何一家收的格式。
被拒的图留在历史里，**之后每个请求都被拒**，对话就封死了。

## 一张图怎么缩（`shrink.ts`）

先尺寸、后字节：

- **长边 2000、面积 3.75 MP**。2000 是 Claude Code、opencode、pi 的共同值，也是 Anthropic 旧文档里
  「一次超过 20 张图」时的边长上限；3.75 MP 是 Claude 4.7 以后高分辨率档的上限（4,784 个 28×28 视觉
  token），没有哪家看得比这更多，多出来的只是上行时间。
- **软目标 512 KB，硬上限 3.75 MiB**。512 KB 是 Claude Code 和 oh-my-pi 收手的地方；3.75 MiB 编成
  base64 正好 5 MiB，是 Bedrock 的单图上限——很多中转背后就是 Bedrock。
- **格式按来路分**：PNG/GIF/WebP（屏幕来的）走 `sharp`——PNG 先试，超了 512 KB 再试 JPEG q90/80/70；
  JPEG/HEIC/AVIF（相机来的）走 `photo`——JPEG q85/75/65。阶梯上第一个落进软目标的就用；都没落进去取
  硬上限以内最小的；再不行宽高各缩四分之一重来，最多四次。q90、q80 是拿 11px 的 devtools 截图缩到长边
  1568 逐像素对比过的：字和 PNG 一样能读；缩到 768 的 q70 就读不出来了，所以缩略图（`gist`）只当
  「这张图大概是什么」用。
- **已经合格的不碰**：在所有限制以内、格式三家都收、不超过软目标，原字节放行，连解码都不做。超过软目标
  但在硬上限以内的，只有编出来明显更小（小一成以上）才换——不然同一张图在输入框缩一次、到主进程再被
  JPEG 压一次。
- JPEG 没有透明通道，编之前铺白底（`nativeImage` 的 `toJPEG` 会把透明处编成黑色，实测过）。

不用 WebP 输出：主进程的 `nativeImage` 编不了，部分 OpenAI 兼容的第三方模型也不收。

## 在哪一层缩

**进来时缩一次**，所有入口：

- 三个输入框的附件、粘贴、拖入，手机上选的照片：`readPickedFiles` 先用 canvas 缩，再决定手机上要不要走
  上传。12 MP 的照片缩完几百 KB，直接随消息走，不再整张传到桌面让 agent 再去读。
- 查看器里「标注 → 完成」、画廊里的标注副本：`fitDataUrl`，标注器交回的是原尺寸 PNG。
- 人发的每条消息：`AgentSession` 在写入记录之前用主进程的编解码器再过一遍（`fit-entry.ts`）。输入框缩过的
  图在这里只是读一下文件头；canvas 解不了的 HEIC、TIFF 在这里由 `sips` 转掉。
- 每个工具结果：`tool-run.ts` 在结果落盘之前过一遍——`read` 读的图、MCP 返回的图、浏览器截图。缩过的
  工具截图后面跟一句 `[Image: original WxH, displayed at wxh. Multiply coordinates by N …]`（Claude Code
  和 pi 的原话），模型要拿坐标去点的时候能换算回去。人发的图不加这句。
- `read`：有编解码器时读到 20 MiB（和 opencode、oh-my-pi 一样），反正进历史之前会缩；没有时上限是能
  发出去的 3.75 MiB。

**存的是缩过的那份。** 理由：模型从来看不到比这更多的像素；每一轮都要从磁盘回填全部图片进内存，原图让一个
13 张图的对话每次加载读 19 MB；窗口和手机显示的也是这一份。拖进来的文件原件还在原处，附件上留着路径，
「打开」走的是它；粘贴的截图留下的是长边 2000 的那份，查看器里放大看足够。标注链路（`ImageContent.from`）
记的是 `session-media` 里的名字，缩过之后照样成立。`image_generate` 拿对话里最新一张图当底图二次生成时，
人发的照片给到的也是这一份——生图接口自己会把输入缩到 1024–1536，2000 绰绰有余。生成出来的图不受影响：
它们由工具单独存成原图，工具结果里只有文字。

## 发出去时按预算带（`request-images.ts`）

`streamAssistant` 是所有请求的必经之路（agent 循环、压缩摘要、连通测试），每个请求在交给适配器之前过一遍：

1. **按模型再收一次尺寸**。Claude 4.7 以前的标准档只看长边 1568、面积 1456×819（文档自己给 1920×1080
   的答案），就给它这么大；其余模型用进来时的尺寸，只读文件头。改之前存下的老会话里的原图在这里缩，结果按
   内容哈希缓存（64 条 / 64 MB），同一张图下一个请求直接复用。
2. **历史图预算**（`request-budget.ts`）：全尺寸最多 10 张或 4 MiB，超了从最老的开始降成缩略图（长边 768、
   约 30–50 KB），缩略图最多 20 张，再超就降成一句话。一次切到 60%，下一张图进来不会马上又切——切口
   改变请求前缀、打碎 prompt cache，所以要隔几张才动一次（opencode 25→15 MiB、Claude Code 一次多剔
   20 张是同一个道理）。判定每次从对话开头重放，所以已经降下去的图在之后每个请求里都是降下去的，不会
   来回跳。
3. **从不降级的**：这一轮人发的图（问的就是它们），和刚到的那条消息里的图（模型上一步刚要的截图）。
4. 硬上限兜底：张数 90、图片合计 16 MB，超了不管保护不保护，最老的先换成一句话——一个注定被拒的请求
   对谁都没用。

说明文字是给模型的（英文，和别的占位一致）：降成缩略图的写明「这是缩小的副本，小字可能看不清，需要
就重新截或请用户重新附上」；降成一句话的写明「看不到了，别凭印象描述，需要就重新取」——后半句照
opencode 的写法。

**只改发出去的那一份。** 适配器拿到的是新的消息数组，会话记录、存储和界面上的图一张不少。

### 没有编解码器的宿主（CLI）

什么都缩不了，所以边界只做一件事：不发供应商会拒的东西。格式不在 PNG/JPEG/WebP（加上 Claude 和 GPT 收的
GIF）里的、超过 3.75 MiB 的、长边超过 8000 的、一次超过 20 张时长边超过 2000 的，换成一句
`[image omitted: …]`。其余原样发，让供应商自己缩。历史预算照样生效，只是没有缩略图那一档。

## 改后（同一组样本、同一个探针）

`image-shrink-probe.ts 改前` 与 `改后` 各跑一次（模型配成 `claude-opus-4-6`，标准档）。改后的剧本多两张图：
第二轮带一张从查看器「标注 → 完成」交回的图，第三轮粘贴一张 7 MB 的 4K PNG，所以后三轮是在多带图的情况下比的。

| 请求 | 改前请求体 | 改后请求体 | 15 KB/s 下（改前 → 改后） |
|---|---|---|---|
| #1 发 13 张图 | 24.23 MB | 2.99 MB | 1654 s → 204 s |
| #2 `read` 调用 | 24.23 MB | 1.76 MB（7 张旧图成了缩略图） | 1654 s → 120 s |
| #3 `read` 之后 | 25.67 MB | 2.02 MB | 1752 s → 138 s |
| #4 粘贴后再问 | 25.67 MB | 2.23 MB | 1752 s → 152 s |

- `session-media` 落盘 19.27 MB → 4.52 MB；HEIC 从 `[unsupported image: image/heic]` 变成一张 JPEG，气泡里也画得出来了。
- 发出去的每张图长边 ≤ 2000（标准档 Claude 是 1456×819）、单张 ≤ 400 KB；`read` 读的 4K 截图带了坐标换算那句话。
- 放进 13 张图的耗时 2.4 s → 3.0 s（canvas 解码、编码）。
- 本机回环上「按下发送到假端点收齐」第一轮 0.3 s → 2.0 s：HEIC 走 `sips` 约 0.7 s，标准档 Claude 要把 13 张
  从 2000 再缩到 1456 约 1 s，之后的请求走缓存（0.04–0.5 s）。上行稍慢一点就是净赚：10 Mbps 上改前要传
  20 s，改后 2.4 s 加这 2 s。新一些的模型（4.7 以后、GPT、Gemini）不需要再缩，这一秒没有。

## 没覆盖的

- Windows、Linux 上主进程解不了 HEIC、TIFF（`nativeImage` 只认 PNG/JPEG，`sips` 只在 macOS）：这类图进来时
  原样，发出去时换成一句说明，不会让请求被拒。
- 插话（回合进行中发出的消息）在排队时异步缩，如果循环先把它取走了，存下的是原样那份；发出去的那份照样在
  边界上缩过。
